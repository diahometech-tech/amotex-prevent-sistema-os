# Revisão de erros — 2026-07-10

**Nota sobre o período coberto:** este relatório foi gerado no primeiro teste manual da skill
`nexusflow-error-review`/`scripts/nexusflow-fetch-logs.sh`, antes de o `log_date_format` do PM2
ter sido aplicado em produção (PR #62). Por isso os logs abaixo **não estão filtrados por
janela de tempo** — cobrem todo o histórico acumulado do processo `nexusflow` no PM2, não só as
últimas 24h. Recomenda-se rodar de novo depois que o PR #62 for mesclado e o PM2 reiniciado com
`pm2 restart ecosystem.config.js`, para um recorte diário confiável.

## Resumo

2 problemas distintos identificados nos logs, ambos aparentando ser de um mesmo período histórico
(não confirmável sem timestamp) — nenhum indício de que estejam ativos agora.

## Achado 1: `error: column "deleted_at" does not exist`

- **Local:** `src/lib/db-postgres.ts` — `ensureSchema()`/`runSchemaMigration()`
- **Causa raiz:** `ensureSchema()` cacheava a *promise* de migração do schema mesmo quando ela
  rejeitava no meio (ex.: `ALTER TABLE dossiers ADD COLUMN IF NOT EXISTS deleted_at` nunca chegou
  a rodar). Depois disso, **toda** query do processo (login, listagem de dossiês) passava a
  falhar com esse erro, pra sempre, até um restart manual do processo.
- **Já documentado em nexusflow-context?** Sim — item 1 de "Incidentes e lições aprendidas"
  já descrevia exatamente esse sintoma ("fazendo parecer que registros tinham sumido — na real
  era erro de query, nenhum dado foi perdido"), listado como causa raiz "ainda não corrigida".
- **Usuários/ações envolvidas (via logs):** login (qualquer usuário) e listagem geral de
  dossiês — não específico de um papel.
- **Proposta de correção:** extrair a migração para função própria e resetar o cache em caso de
  falha, permitindo retry na próxima chamada. — **Confiança: alta**
- **Ação tomada:** PR draft [#65](https://github.com/Dmc9494/nexusflow/pull/65) aberto.

## Achado 2: rajada de `Could not find a production build` / `client reference manifest ... does not exist`

- **Local:** logs do PM2, sem localização de código específica (erro de infraestrutura/build do
  Next.js, não de lógica de aplicação).
- **Causa raiz provável:** o processo foi reiniciado (`pm2 restart`) num momento em que `.next`
  estava ausente ou incompleto — condiz com múltiplos ciclos rápidos de `✓ Ready in Xms` logo
  depois, sugerindo um período de instabilidade que se resolveu sozinho (auto-restart do PM2)
  ou por intervenção manual. Não achei uma causa de código pra isso — é sintoma de timing entre
  build e restart, não um bug de aplicação.
- **Já documentado em nexusflow-context?** Não diretamente, mas é adjacente ao aviso já existente
  sobre corrupção de cache do Turbopack em dev (esse caso é produção, `next start`, mecanismo
  distinto, mas mesma categoria de "build vs. processo says restarted at wrong time").
- **Proposta de correção:** nenhuma mudança de código — recomendo apenas confirmar que o
  `deploy.yml` sempre completa `npm run build` antes de `pm2 restart` (já é o caso hoje, a
  sequência já está correta) e evitar reiniciar o PM2 manualmente na VPS sem rodar `npm run build`
  antes (mesma classe de armadilha do `AGENTS.md`, só que em produção).
- **Ação tomada:** nenhuma — documentado para referência; sem indício de recorrência ativa.
